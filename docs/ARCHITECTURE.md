# Architecture

```
            text
             |
   lexer     |  lex_line()          "G1 X10 F200" -> [G 1] [X 10] [F 200], with columns
             v
   parser    |  parse_block()       words -> Block: G/M codes, one value per letter, checks
             v                      repeated letters and modal-group conflicts
 interpreter |  interpret()         Blocks -> Segments. The only stage that knows G-code:
             v                      units, planes, offsets, tools, cycles, feed, spindle
      std::vector<Segment>          explicit moves in mm, work coordinates
      /       |        \      \
 planner   linter    stats    svg
 time      LN001-9   totals   drawing
```

`analyze()` (analysis.hpp) runs the whole chain, and `report.hpp` turns the
result into text or JSON. The CLI (`cli/main.cpp`) and the web page
(`web/wasm_bindings.cpp`) are both thin layers over those two calls, which is
why the web page and the CLI always agree.

## The Segment

Everything after the interpreter works on this one struct (`segment.hpp`):

- `type`: rapid, linear, arc, dwell, tool change or pause
- `start`, `end`: tool tip in work coordinates, mm
- for arcs: `center`, `plane` and a signed `sweep` in radians
- the state it was cut with: `feed`, `spindle_rpm`, `spindle_on`, `tool`
- `machine_offset`: add it to a point to get machine coordinates
- `from_cycle`: generated by a drilling cycle
- `line`: the source line, for messages

Dwells, tool changes and pauses are Segments too, so the planner sees them in
order and can stop there.

## Stages

**Lexer** (`lexer.cpp`). One line at a time; drops comments, reads
letter/number pairs. Never throws: problems become diagnostics and the rest of
the line is still read.

**Parser** (`parser.cpp`). Groups a line's words into a `Block`. G codes are
stored in tenths (`G91.1` is 911) so decimal codes are exact integers. Knows
the modal groups, so `G0 G1` on one line is an error here, before anything
runs.

**Interpreter** (`interpreter.cpp`). Holds the modal state and executes each
block in the RS-274 order (feed, spindle, tool change, plane, units, offsets,
distance mode, then motion). Positions are converted to mm at once. It works
line by line: parse one block, run it, forget it.

**Planner** (`planner.cpp`). Splits arcs into short chords, gives each piece a
speed limit (feed, or for rapids the fastest the axes allow in that
direction) and an acceleration limit, then:

1. junction speed at each corner from the junction-deviation rule (as in Grbl);
2. backward pass: every piece must be able to slow down for the next one;
3. forward pass: and able to speed up from the previous one;
4. a trapezoidal profile (accelerate, cruise, decelerate) per piece.

**Linter** (`linter.cpp`). Each rule is a small class with `code()`,
`summary()` and `check()`. `make_default_rules()` lists them.

**Stats** (`stats.cpp`), **SVG** (`svg.cpp`), **report** (`report.cpp`):
totals, the top-view drawing, and text/JSON output.

## Errors

Problems in the *program* are `Diagnostic`s: they never stop the run. Problems
in the *machine config* throw `ConfigError`, because a wrong config makes
every number meaningless; the CLI turns that into exit code 2.
